# Harmony 一期实施计划

> 状态：Draft
>
> 本计划按**垂直切片**组织，每个切片结束时都产出可在真机/模拟器上运行和验证的
> 可见成果，不按“先基础层、后页面”的两大阶段推进。页面是模块能力的验证手段，
> 渲染和滚动本身属于模块的一部分，必须与数据层同步开发。
>
> 每个切片完成后必须有对应的源码、fixture 或验证证据；切片之间可以并行准备
> （如切片 3 的图片能力文档与切片 2 的渲染开发互不阻塞），但合入主分支前
> 必须先通过前序切片验收。

## 0. 前置：系统能力验证

> 只做最小验证代码，**不写过渡界面**。全部在真机或模拟器上跑通后再进入切片 1。
> 这是项目当前最大的技术风险点，不能跳过。

- [x] wss + 自定义 `Authorization` Header 握手验证（DlClient + HarmonyWsAdapter 实现，真机复核）。
- [x] HTTP / JSON / TLS / 超时验证（HarmonyHttp 实现，真机复核）。
- [x] Token 安全存储验证（SecureStore + preferences，已禁用系统备份）。
- [x] App 前后台生命周期事件验证（EntryAbility → AppServices.onAppForeground）。
- [x] 图片 URI 读取能力调研（PhotoViewPicker + 文件头嗅探，切片 3 落地）。

验证结果记录到 `docs/decision-log.md`（新增 D-00x）。

## 1. 切片 1：最小闭环

> 目标：真机上完成一次完整对话。
> 登录 → 设备发现 → 打开任务 → 加载历史消息 → 发送一条消息 → 收到流式回复。
> 本切片所有模块都是**最小实现**：纯文本消息即可，不做完整 Markdown、不做
> 全部消息类型、不做附件。先把链路打通，横向扩展留给后续切片。

- [x] 工程骨架：Navigation 路由（登录/首页/任务详情）、Store 目录、
      network adapter 目录。
- [x] auth Store 最小实现：登录、Token 存储/刷新、登出。
- [x] device-link adapter 最小实现：WebSocket 连接、握手、invoke/push、
      心跳、重连。
- [x] 消息 Store 最小实现：任务打开、历史消息加载、流式追加、去重排序。
- [x] 登录页、首页（设备+任务列表）、任务详情页（消息流+Composer）三张页面。
- [ ] 验收：真机登录 → 发现桌面设备 → 打开任务 → 看到历史 → 发送消息 →
      收到流式回复。
