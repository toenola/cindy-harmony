# Harmony 决策记录

## D-001：采用独立 `apps/harmony`

- 日期：2026-08-04
- 状态：已决定
- 决策：Harmony 客户端放在 `apps/harmony`，不改造成 `apps/mobile` 的第三个平台。
- 原因：ArkUI + ArkTS 拥有独立 DevEco 工程、原生依赖、资源、构建和发布边界；避免影响 iOS / Android。

## D-002：采用 ArkUI + ArkTS

- 日期：2026-08-04
- 状态：已决定
- 决策：使用 ArkUI 原生 UI 和 ArkTS，不追求仓颉路线。
- 原因：稳定性、工具链和 ArkUI 集成优先；现有 Cindy 共享逻辑主要是 TypeScript，ArkTS 的迁移和理解成本更低。

## D-003：Harmony 端是远程控制端

- 日期：2026-08-04
- 状态：已决定
- 决策：Agent、工作目录、数据库、CLI、MCP 和插件继续运行在电脑端。
- 原因：一期目标是鸿蒙手机远程控制桌面 Cindy，不移植桌面执行环境。

## D-004：核心消息和 AI 交互一期完整实现

- 日期：2026-08-04
- 状态：已决定
- 决策：任务详情、历史消息、消息流、图片上传、Permission、Ask User、Plan Review 不做半套。
- 原因：历史消息包含结构化 Tool、Thinking、Todo、媒体和交互状态；事后补齐会导致历史数据无法可靠恢复。

## D-005：Device Link 不重新设计

- 日期：2026-08-04
- 状态：已决定
- 决策：Harmony 端实现平台适配和必要的 ArkTS Client，继续兼容当前 Device Link。
- 原因：保持桌面端和现有 Mobile 的互操作，避免维护第二套远程协议。

## D-006：ArkWeb 只用于复杂内容

- 日期：2026-08-04
- 状态：已决定
- 决策：整体 UI 使用 ArkUI；Mermaid、Math 和复杂 HTML/媒体内容可以局部使用 ArkWeb。
- 原因：既保持 Harmony 原生页面结构，又避免为复杂文档格式重复实现浏览器排版。

## D-007：第一期暂不做 Issue Confirm 手机提交

- 日期：2026-08-04
- 状态：沿用现有策略
- 决策：Harmony 端识别 `issue_confirm` 并提示回桌面处理，不提供 GitHub Issue 编辑和提交表单。
- 原因：它不是普通 AI 交互闭环；当前 Mobile 已采用相同的安全降级策略。

## D-008：空工程构建通过，暂不承诺真机验证

- 日期：2026-08-04
- 状态：部分完成
- 决策：DevEco 空工程的 `entry:assembleHap` 已构建成功；在模拟器或真机实际安装运行前，不宣称 Harmony 运行验证通过。

## D-009：开发顺序改为垂直切片

- 日期：2026-08-04
- 状态：已决定
- 决策：实施计划从「先完整基础层、后页面」改为「垂直切片」：每个切片以用户可见成果收尾（切片 1 是最小闭环：登录→设备发现→打开任务→发消息→收流式回复），页面与数据层同步开发。
- 原因：App 的渲染、滚动、流式合并等能力本质是页面的一部分，单测无法替代真机验证；按层推进会导致前期看不到成果、后期 UI 问题集中爆发。模块划分与 Store 架构保持不变，只重排交付顺序。
- 配套：`docs/implementation-plan.md` 已按切片重写。

## D-010：任务列表滑动操作不支持全滑直达

- 日期：2026-08-11
- 状态：已决定
- 决策：Harmony 任务列表右滑和左滑只露出置顶 / 取消置顶、归档 / 恢复按钮；继续滑动并松手不得直接执行操作，用户必须点击按钮后才执行。
- 原因：全滑直达容易在浏览列表时误触，归档和置顶都需要明确的点击意图。该安全交互是 Harmony 相对当前 Mobile 实现的有意差异。

## D-011：富组件回答原生渲染的 Harmony 差异

- 日期：2026-10-22
- 状态：已决定
- 决策：`cindy-ui` 解析逐行移植共享 `richAnswer.ts`（上限、白名单、算术与可读文本一致），呈现用 ArkUI 原生组件；以下为有意差异：
  - `video` / `audio` 节点与 YouTube 链接降级为可点链接（YouTube 规范为 watch 链接），不内嵌站点播放器；`image` 复用正文 Markdown 图片链路。
  - JSON `null` 属性值按缺省处理（ArkTS 记录不承载 null），`patch` 传 `null` 不会清空该属性。
  - 折线图刻度不加千分位分隔符。
  - SVG 与折线图用 Canvas 绘制，资源色通过 `getOverrideResourceManager()` 按当前系统模式解析；深浅色切换由 EntryAbility 的配置通知与回前台同步写入 `cindyColorMode` 触发重绘。
- 原因：Harmony 没有安全的站点播放器嵌入链路（ArkWeb 仅用于复杂内容，见 D-006）；其余差异只影响边缘输入，不改变可读内容与交互语义。

## D-012：v1.3.3 消息呈现增量中无需移植的部分

- 日期：2026-10-22
- 状态：已决定
- 决策：
  - Harness 切换边界（#6260）不移植：Harmony 的待发送消息始终作为独立队列气泡排在全部历史之后，不像 Mobile 把乐观气泡插进历史，所以切换行不会被越过；回显后按 Host 落库时间排序，与 Mobile 测试夹具一致。
  - 跨电脑来源任务 `deviceId::sessionId` 不新增处理：Harmony 的来源任务标签本就只提供复制 ID、不跳转。
  - 失败采样折叠时，工作组身份只跳过失败采样正文，不改用共享的「首个非消息项」锚点，以保持 Harmony 已有工作组 key 稳定。
- 原因：上游修复针对的是 Harmony 不存在的实现路径；照搬只会引入无用代码或改变现有节点身份。

## D-013：厂商信息统一通过电脑端获取

- 日期：2026-10-22
- 状态：已决定
- 决策：Harmony 禁止直接调用模型厂商或 Agent 厂商接口获取信息；模型目录、能力、账户配额与用量、Agent 状态等统一经 Device Link 从电脑端读取。厂商通信、认证与缓存由电脑端负责，鸿蒙不持有厂商凭证，也不在电脑不可用时回退直连厂商。Cindy 自身的登录、设备互联和附件链路不受影响。
- 原因：用户明确要求区分鸿蒙直连与电脑端代查，不能把电脑端访问厂商也判成违规；原「账户配额与用量」本就经电脑端获取，用户确认恢复保留该入口，不因这一边界删除合规的电脑端能力。
