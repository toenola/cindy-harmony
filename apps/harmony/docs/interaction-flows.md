# 交互确认流程

> 状态：一期必须实现

## 1. 通用状态机

```text
pending
  ↓
展示请求
  ↓
用户编辑或选择
  ↓
提交中
  ↓
resolved / rejected / expired / failed
```

通用要求：

- 使用远端 request id 去重。
- 提交后锁定操作，防止重复 resolve。
- 页面返回或 App 切后台不能丢失待处理请求。
- 请求过期时显示明确状态。
- 网络失败时保留用户输入，允许重试。
- 远端已处理但本地未收到响应时，恢复任务状态而不是再次提交。

## 2. Permission

支持：

- 允许一次。
- 始终允许。
- 拒绝。

展示：

- 工具或操作名称。
- 必要的风险说明。
- 关键输入摘要。
- 当前任务和设备上下文。

提交后：

- 禁止重复点击。
- 等待远端结果。
- 失败时显示重试入口。
- 远端完成后回到消息流。

## 3. Ask User

支持：

- 单选。
- 多选。
- 自定义文本输入。
- Skip。
- 多步骤问题。
- 上一步和下一步。
- 草稿暂存和恢复。
- 最终结果确认。

不能只做一个单文本弹窗。问题的选项结构、选择结果和 Skip 语义必须与桌面端协议一致。

## 4. Plan Review

支持：

- 计划内容查看。
- 章节或步骤展开/收起。
- 计划编辑。
- Approve。
- Feedback。
- 反馈文本。
- 提交后冻结。
- 计划更新后的再次渲染。
- 重复提交保护。

计划内容应支持长文本、代码和必要的 Markdown；复杂内容可以使用 ArkWeb，但不能因为页面空间不足而截断计划事实。

## 5. issue_confirm

当前策略：

- Harmony 端识别 `issue_confirm`。
- 显示它需要回桌面处理。
- 不在 Harmony 端提交 GitHub Issue。

如果以后需要在手机端提交 Issue，必须新增独立产品决策，不应在一期偷偷扩展。

## 6. 测试矩阵

每类交互至少覆盖：

- 正常提交。
- 重复点击。
- 网络断开。
- Token 刷新。
- App 后台再前台。
- 请求过期。
- 远端已处理。
- 桌面端取消或拒绝。
- 任务被停止或撤权。
