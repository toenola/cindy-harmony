排序理由：阶段 1 修的是“做错事”的问题（误报成功、错的模型、错的额度），优先级最高；阶段 2 的修复小且能减少后续联调的噪音，因此提前到历史改造之前；5a 只改投递判定、不碰持久数据，放在最后。

## 4. 本期不做

以下仍需另行选择，不随本期交付：

- **持久发件箱（原 5b）**：按账号隔离、先落盘再发布，接管现有队列所有权，附件文件归属与清理，强杀重启后继续核对和投递。后续版本启动时须先提交设计（账号归属、消息所有权、存储满、迟到缓存写入不覆盖已确认消息、旧 Host 兼容），评审通过再写代码。
- **可选体验**：Claude/SuperGrok 额度与重置倒计时、token 速度图、任务标签、折叠分组状态聚合、外观模式（跟随系统/浅色/深色）、图片查看器增强／SVG、系统分享接收、图片标注、长期驻留性能、大附件分块直传。
- **原评估未提到的既有差距**（在上次基线之前 Mobile 就已有，不属于本次增量）：新建任务的 worktree 开关与源分支选择、模型收藏、输入框推荐指令／空态推荐任务、双击标题改名。
- **独立产品能力**：跨账号共享任务、远程 Agent 选择与供应商分享／供应商组（B2 只做只读防护，不做选择）、伙伴／群聊／Todo、完整 Orca 协同、插件页面与调用、远程桌面、完整语音。
- **不需要跟进**：Mobile 移除的是自动化**管理**入口；Harmony 的“自动化”Tab 只浏览自动化产生的任务，与 Mobile 首页自动化分组一致，保留。后台任务状态（#5487）只在桌面远控生效；端点清单容灾、微信登录、验证码 60 秒倒计时（Harmony 已是 60 秒）均与本端无关或已一致。

## 6. 实现交接要点

以下是复核时确认的关键协议细节和容易踩坑的地方。开发前仍须按 `mobile-alignment.md` 完整读一遍对应 Mobile／共享源码，本节只作索引，不能替代读源码。

### 工作方式

- 每个阶段单独提交，提交说明写清阶段编号（如 `feat(harmony): v1.3.2 阶段1 …`），方便逐段 review；带 DCO。
- 新逻辑优先放在 `core/` 的纯函数或 Store，并补 `LocalUnit.test.ets`。`TaskPage.ets` 已有约 1.17 万行，只做接线和布局，不再往里堆判定逻辑。
- 工作区里 `build-profile.json5`（本机签名）、`apps/harmony/build/`、`.workbuddy/` 不得提交；暂存时只加本阶段相关文件。
- Mobile 行为本身与 Harmony 已定规则冲突时（例如分栏、弹层、Composer 的既定交互），以 Harmony 规则为准，并在本目录记录差异。

### 阶段 1

- **A1**：读源 `maker:get-new-maker-defaults [agentKind]`，回写 `maker:apply-new-maker-draft-pref`。旧 Host 返回 `CHANNEL_NOT_ALLOWED` 时回落目录默认，不报错。用户在本页的显式选择优先于迟到的读取结果；按设备 + Agent 区分异步结果，切设备或 Agent 后丢弃旧结果。模型未落定前不能创建任务（Mobile #5706）。关闭模型的判定照搬 `apps/mobile/src/session/modelReselection.ts`：指定来源看 `agent:providerId:model`；默认来源要求所有来源都关闭才判定需要重选。不要删掉 `latestSessionForAgent` 以外的目录记忆逻辑（v1.3.1 的按账号设备记忆）。
- **A2**：对齐 `interactionModel.ts` 的 `resolveInteractionResilient`。回包 `accepted === false` 时直接抛出“未被接受”，**不能**再查 pending 列表把它改判为成功；只有传输异常才走 pending 补证；旧 Host 返回 void/undefined 视为成功。失败时保留卡片和草稿。`visibleAskOptions` 只替换模型自带的“其他（说明）”类逃生选项，保留“其他任务”这类实质选项，按共享层规则匹配，不要自己写关键词表。
- **B3**：对齐 `packages/maker-shared/src/interaction.ts` 的 `permissionSourceDescription` 和描述去前缀逻辑；自动审批故障提示单独读取 `metadata.imSourceDescription`，不覆盖来源。来源文本可选中复制。
- **B1**：`maker:input:get-projection` 回包的 `usageLimitWait.resumeAt`（有限正数毫秒才有效，否则视为无等待）；只在队列有 error 且有等待时显示“将于 X 自动继续 · 取消”；取消调用 `maker:input:cancel-usage-limit-wait [sessionId]`，旧 Host 拒绝时隐藏取消入口。时间按界面语言格式化。
- **B2**：Harmony 目前完全不解析 `agentDeviceId`。会话行要解析该字段，pending agent-switch intent 也要解析 `agentDeviceId`（`undefined` = 位置不变，`null` = 改回被控电脑）；语义见 `apps/mobile/src/session/sessionAgentSwitch.ts` 的 `effectiveAgentDeviceId`。Agent 不在被控电脑时：显示 Agent 所在电脑名，不显示被控电脑的账号额度（任务价值与上下文仍可显示），模型／Agent 切换置灰并说明原因。Orca（`orcaRole` 非空）和 SSH（`remoteHostId` 非空）任务沿用 Mobile 规则，不展示 Agent 切换。

### 阶段 2

- **A5**：对齐 `packages/device-link/src/client.ts` 中 `connectNow` 的 `keepInFlightAttempt`。回前台时，只有在当前连接尝试仍未超过握手看门狗**本次启动时记录的墙钟截止时刻**、且没有退避计时器时才保留连接；网络切换等其他入口不受影响。注意 WebSocket 打开后看门狗会重新计时，不能按 `connect()` 起算的总时长判断（上游 `32bbf154f` 修的就是这个）。Harmony 对应 `DlClient.connectNow` 和 `handshakeTimer`。
- **B4**：对齐 `packages/device-link/src/invokeScheduler.ts`：同时在途不超过 12 个，其中后台类不超过 4 个，排队上限 128，超出时返回 `BACKPRESSURE`；后台类 channel 名单见 `invokePolicy.ts` 的 `BACKGROUND_INVOKE_CHANNELS`。出队前复验取消与归属。Harmony 已能识别 `BACKPRESSURE`（`DlClient.ets:46`），要补的是限流本身，以及 UI 显示“电脑繁忙”而不是“失败”。

### 阶段 3

- **A3**：`local-db:messages:view [sessionId, { before, lazyDetails: true, workLines: true }]`。推送 `maker:history-work-patch` 带 `baseRevision`（见 `packages/maker-shared/src/historyView.ts` 的 `HistoryWorkPatch`），只在本地条目 revision 等于 `baseRevision` 时应用，否则丢弃并等下一次读取。展开详情尚未返回时保留已有活动行（上游 #5821）。不要照搬 `HISTORY_VIEW_PAGE_BYTES` 等字节常量去扩大请求，先核对 Harmony 现有预算。

### 阶段 4

- **A6**：来源字段在 `agentMeta.sourceDevice`／`agentMeta.sourcePlugin`，读取与显示规则照搬 `packages/maker-shared/src/messageSource.ts`；`shouldShowSourceDevice` 规定查看者就是发送设备时不显示，Harmony 需用自己的 Device Link 设备 ID 比较。目标模式裁决块只在显示层剥离（`goalVerdict.ts`）。产品规则见 `docs/product-rules/message-source.md`。

### 阶段 5a

- 查询时 `maker:input:get-projection` 要带第二个参数 `{ deliveryClientIds: [...] }`（最多 64 个，每个最长 256 字符），Host 才会返回 `inputDeliveryVersion: 1` 和 `deliveryReceipts[{ clientId, state }]`，state 为 `pending`／`accepted`／`removed`／`unknown`。当前 Harmony 只传 `[sessionId]`。没有 `inputDeliveryVersion` 的旧 Host 保持现有行为。只有 `accepted` 才能证明 Host 已持久接收；`unknown` 或拿不到回执时不能自动重发。参考 `apps/mobile/src/session/durableOutboxDelivery.ts` 的判定，但本期不引入落盘。

## 7. Review 关注点

开发完成后按以下各项 review：

- 每个阶段的完成标准是否都有对应单测；旧 Host 回退路径（`CHANNEL_NOT_ALLOWED`、字段缺失）是否覆盖。
- A2：`accepted:false` 是否会被任何路径（重试、pending 补证、`stateGeneration` 分支）改判为成功。
- A5／B4：前台恢复是否仍会 terminate 有效握手；限流是否会把单个 peer 的拥塞扩大成整条连接重连（故障半径三问）。
- A3：迟到的 patch 和响应是否可能覆盖新数据；阅读位置和草稿是否受影响。
- B2：Agent 在其他电脑的任务上，是否还存在显示被控电脑额度或能换模型的入口。
- 新 UI 是否实现 Light/Dark 和五种语言；未做真机目检的项是否如实记录。
- 提交范围：没有混入签名配置、构建产物或 `apps/harmony` 以外的改动。
