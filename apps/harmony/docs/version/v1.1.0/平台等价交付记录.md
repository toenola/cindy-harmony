# v1.1.0 阶段 6：平台等价交付记录

本文记录 Mobile 平台特有项在 Harmony 的等价交付证据，或明确的外部阻塞。
按开发计划要求，**不允许只写「不适用」后关闭**。

## 1. beta / release 构建与分发身份

**状态：已定义口径，未接入分发平台（外部依赖）。**

Harmony 不引入 Expo OTA。构建身份以现有工程配置为唯一来源：

| 身份项 | 来源 | 说明 |
|---|---|---|
| `versionName` | `AppScope/app.json5` | 对外版本号，发布前与本目录版本一致 |
| `versionCode` | `AppScope/app.json5` | 单调递增整数，见下方策略 |
| `appVersion` | `entry/src/main/ets/AppConfig.ets` | Device Link 上报与设置页展示 |

`versionCode` 递增策略：**每次对外可安装产物递增 1**，不复用、不回退。
beta 与 release 使用同一递增序列（不分叉），避免两条渠道产生相同 versionCode
导致覆盖安装行为不确定。

渠道不串线的约束：
- debug / beta 产物仅用于内部验证，不写入本目录作为发布记录；
- 正式发布使用现有签名配置产出的 `entry-default-signed.hap`；
- 不在 Harmony 端私造 manifest 或自定义更新协议。

**外部阻塞**：Harmony 应用市场上架、分发渠道账号与灰度策略需要平台侧材料，
不在客户端代码范围内。用户决定发布渠道后再补此节的实际渠道标识。

## 2. 更新服务（OTA）支持评估

**状态：评估完成，结论为暂不接入（外部契约缺口）。**

- 现有 `cindy-updater` 与 Desktop Electron 更新链路面向桌面产物（差分包、
  签名校验、重启替换），其 manifest 与安装语义都基于桌面可执行文件；
- HarmonyOS 应用更新由系统应用市场接管，第三方应用不能自行替换已安装 HAP；
- 因此**不复用**桌面更新协议，也不在 Harmony 端伪造「已可 OTA」。

结论：Harmony 版本更新走系统应用市场。若后续需要内部灰度分发，需服务端提供
Harmony 专用的版本查询契约；在那之前该项按外部依赖挂起，客户端不做半成品接线。

## 3. 可选安全观测身份 adapter

**状态：客户端已交付，真实 SDK 接入为发布阻塞。**

交付物：`entry/src/main/ets/core/observability/SecurityObservabilityAdapter.ets`

- `bindUser(userId)`：登录完成、换号后由 `AppServices` 调用；
- `clearUser()`：登出**开始**即调用，避免崩溃 / 强杀上报误归上一个账号；
- 默认实现为安全 no-op：未注入 sink、或当前区域未启用时不上报；
- sink 抛异常一律吞掉，**不阻断认证**；
- **不持久化 userId、不写日志**（userId 不得进入可上传日志）。

语义对照事实源：`apps/mobile/src/auth/AuthContext.tsx` 的 THEMIS 绑定
（登录写入、登出写空串、模块缺失静默降级）。

单测覆盖：缺 SDK、区域未启用、空 userId 归一为清空、换号重绑、sink 抛错不影响
认证（`degradesSecurityObservabilitySafelyAndNeverBlocksAuth`）。

**发布阻塞**：Harmony 侧真实厂商 SDK 未提供。接入前必须完成隐私影响评估、
区域可用性确认、依赖与签名影响评审、冷启动耗时评估，并验证换号与强杀后归属不串号。
在此之前保持 no-op，不影响任何现有功能。

## 4. DevEco 精确工程 / 精确设备 / signed HAP 流程

**状态：已落实为文档化流程（替代 Metro / iOS Simulator 接管）。**

不实现 Metro 接管。等价安全目标已写入 `apps/harmony/项目鸿蒙端开发指南.md`
第 10–11 节，要求：

- 构建与测试始终针对当前 worktree 的 `apps/harmony`，不跨工程；
- 安装前用 `hdc list targets -v` 显式选择 `Connected` 目标，不隐式选设备；
- 只安装现有签名配置产出的 `entry-default-signed.hap`，禁止 unsigned 覆盖；
- 签名不一致时立即停止，交由用户在 DevEco Studio 处理；
- **禁止**为绕过签名问题执行 uninstall、清应用数据或重置模拟器。

本版开发期间实际遵循该流程：所有验证使用 `hvigorw test` 与 `assembleHap`，
未卸载应用、未清数据、未修改签名配置。

## 5. 系统选图器受限授权与 URI 生命周期

**状态：实现已具备，待真机勾选验证（阶段 7）。**

Harmony 使用系统 `PhotoViewPicker`，本身即「用户选择即授权」模型，不申请全图库
权限，因此不存在 iOS 受限相册的等价开关。现有实现位于
`entry/src/main/ets/core/attachments/ImagePicker.ets` 与 `ComposerImageQueue.ets`：

- 只读取选择器返回的 URI，不扫描图库；
- URI 读取失败 / 失效时进入可重试失败态，用户可重新选择（不扩大权限）。

阶段 7 需在真机确认：只选部分照片仍可正常读取与上传；应用重启后旧 URI 失效时
给出可恢复的重新选择提示。
