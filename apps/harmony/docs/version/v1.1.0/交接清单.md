```bash

export R=/Applications/DevEco-Studio.app/Contents

# 单测（比 HAP 构建更严格，先跑它）
NODE_HOME="$R/tools/node" JAVA_HOME="$R/jbr/Contents/Home" \
  "$R/tools/hvigor/bin/hvigorw" test --mode module -p product=default -p module=entry@default

# HAP 构建
NODE_HOME="$R/tools/node" JAVA_HOME="$R/jbr/Contents/Home" \
  "$R/tools/hvigor/bin/hvigorw" assembleHap --mode module -p product=default \
  -p module=entry@default -p buildMode=debug
```

必读：仓库根 `AGENTS.md`、`apps/harmony/项目鸿蒙端开发指南.md`、
`apps/harmony/docs/mobile-alignment.md`、本目录 `开发计划.md` 与 `验收与发布状态.md`。

**两个环境陷阱**（我踩过）：

1. `hvigorw` 必须设 `DEVECO_SDK_HOME`，否则报
   `Invalid value of 'DEVECO_SDK_HOME'`。
2. **HAP 构建不编译未被引用的文件**。我曾写完一个模块、HAP 构建通过，
   实际那个文件从未被编译（追加一行故意的类型错误仍能构建成功）。
   验证某文件真的被检查：临时追加 `const X: number = "s";` 看构建是否失败。
   Local Test 的 ArkTS 编译更严格（它抓到过 HAP 构建漏掉的错误导入路径）。

## 1. 唯一的硬阻塞：无 API 26 运行环境

**这是最高优先级，其余待办几乎都依赖它。**

现状：

```
hdc list targets -v      → 6HR0226409030343  USB  Offline    （真机未连上）
devecocli emulator list  → 5 台模拟器全部 HarmonyOS 6.1.1 (API 24)，状态 stopped
build-profile.json5      → compatibleSdkVersion / targetSdkVersion 均 26.0.0
```

API 24 模拟器装不上本产物；真机 `Offline` 且按开发指南不得擅自操作真实设备。

**解除条件**：提供 API 26 (HarmonyOS 7.0+) 模拟器镜像，
或由用户确认可操作该真机并使其进入 `Connected`。

**被它挡住的验证项**（详见 `验收与发布状态.md` §3.1）：

- signed HAP 覆盖安装与启动；
- **会话分享全链路实际出图 + 系统分享面板**（从未真机跑通，见 §2）；
- 窄屏 / 展开横屏 / Light / Dark 目检；
- 断线重连、长会话、快速切换 20 个任务的内存回落观测；
- PhotoViewPicker 受限选择勾选、URI 失效后重新选择；
- 已有能力回归：收起态 Composer、附件入口、队列草稿保护、发送后收起；
- 队列操作触控区 44vp 实机点按；120Hz 动效与「减弱动态效果」。

安装务必遵守开发指南第 11 节：只装
`entry/build/default/outputs/default/entry-default-signed.hap`，
**禁止** unsigned 覆盖、禁止 uninstall / 清数据 / 重置模拟器绕过签名问题。

### P0：分享分段尺寸未真正约束截图（代码已修，待 API 26 真机确认）

2026-08-24 已按官方组件截图语义修复：`createFromBuilder` 本身没有 width / height
参数，只截取 builder 根组件自身区域，因此页面现在把
`ShareSegmentRequest.widthPx / heightPx` 转回 vp，直接用于 `shareSegmentCanvas`
根节点的固定宽度、最大高度与 `clip(true)`。实际 PixelMap 不再能超过分段计划的
纹理安全高度；短段仍按内容自然高度出图，不会补成整张超高空白图。

分段上限同时改为读取 API 26 `getSizeLimitation()` 的设备真实值，并保留 192px
安全余量。仍需在 API 26 设备上确认实际 PixelMap 尺寸与多图顺序。

实现依据：官方文档说明组件截图只覆盖根组件大小，超出根区域的绘制不会进入截图；
`SnapshotOptions` 只有 `scale`，没有 region / 尺寸字段。

### P1：分享高度靠估算（代码已修，待 API 26 真机校准）

2026-08-24 已移除“渲染项数 × 120vp”的固定估算。现在使用
`UIContext.getMeasureUtils().measureTextSize()`，按分享 builder 的真实字体、行高、
内容宽度与内边距测量每张卡片，再按测量高度顺序装箱。单张卡片自身超过设备上限时
明确提示缩小范围，不再用根节点裁剪静默丢正文。真机仍需校准字体回退、系统字号缩放
与离屏布局测量是否完全一致。

### P2：`packToFile` 的 fd 未在异常路径显式回收之外做重试

`packToCache` 已用 `finally` 关 fd 并 `packer.release()`，逻辑正确；
但同名文件已存在时行为未验证（`OpenMode.CREATE` + 同时间戳同序号的极端情况）。
真机跑一次多图分享确认即可。

## 4. 本版已完成内容（供你判断是否需要复核）

阶段 1–7 的代码与单测均已落地。其中有两处是我对照共享事实源找出的**真实缺陷**，
建议接手时优先理解，避免误改回去：

1. **计划跨轮归属**（`core/messages/MessageRender.ets`）：原实现用会随每次计划更新
   前移的 `previous.lastIndex` 比较用户边界，导致旧计划在新用户消息后更新一次就抹掉
   边界、把后续新计划吞进上一轮。已改为 session 建立时固定的 `userBoundaryIndex`
   锚点（对齐 `packages/maker-shared/src/messageRender.ts`）。
2. **工作时长锚点**（同文件）：原实现始终从段内首个 activity 起算，丢掉了用户发送到
   首个动作之间的等待。已引入 `previousBoundaryMs` 沿三条分组路径透传。

其余：`autoReviewUnavailable` 本地化、Pi `/skill:` 展示投影、roster 传 `sessionId`、
`newSessionDefault` 解析、消息 authority fence 与 800行/64MiB 预算、
1013 双稳定窗（10s / 15min）+ 代次守卫、发送接管尾部、附件乐观标题、
字号缩放上限、分享投影与资源释放、观测 adapter。

**每个行为修复都做过反向验证**（临时回退实现确认对应单测失败，再恢复）。
