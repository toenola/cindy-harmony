# Cindy 鸿蒙端开发指南

> 文档版本：1.1（2026-08-17，DevEco CLI / Skills / MCP 集成版）
>
> 面向后续开发者与 AI 新窗口的工程入口。本文以当前源码为准，说明模块职责、代码定位、开发流程和验证方法；不记录容易过期的功能进度。

## 1. 项目定位与开发边界

- 工程目录：`apps/harmony`，它本身是独立的 DevEco Studio Stage 工程。
- 技术栈：HarmonyOS 6.1 / API 24+、ArkTS、ArkUI。
- 应用形态：鸿蒙端是桌面 Cindy 的远程控制客户端。Agent、任务数据、工作目录和工具仍运行在桌面端。
- 通信链路：Harmony HTTP / WebSocket → Auth API / Device Link Relay → Desktop Cindy。
- 默认范围：只修改和验证 `apps/harmony`；不要顺手改 Desktop、Mobile、共享 packages 或协议仓。
- 行为事实源：用户可见行为以 Mobile（iOS / Android）和共享纯逻辑为准；ArkUI 负责鸿蒙原生呈现，不另造状态机。
- 协议事实源：wire protocol 以 `cindy-protocol` 为准，`core/device-link/DlProtocol.ets` 只保留 Harmony 所需子集。
- 主题要求：所有新增或修改的 UI 同时实现 Light / Dark，颜色走同名语义资源 token。

三条不可破坏的归属原则：

1. 页面不直接创建 HTTP / WebSocket，不直接拼 Device Link envelope；远程行为进入 Store 或 Service。
2. 原始数据解析、协议适配和长生命周期状态放在 `core/`；页面只组织布局和用户交互。
3. 可独立验证的分类、排序、解析、投影和状态机尽量写成纯函数，并在 `entry/src/test/LocalUnit.test.ets` 补单测。

## 2. 新窗口接手：5 分钟最短流程

在仓库根目录开始：

```bash
git status --short --branch
git branch --show-current
```

然后按顺序执行：

1. 读根目录 `AGENTS.md`，确认本次任务触发的专项规则。
2. 读本文件；首次定位仓库时再读 `docs/dev-rules/repo-map.md`。
3. 在第 6 节“需求到代码定位表”找到主要入口，不要先全仓盲搜。
4. 若修改用户可见行为，必须先读 `apps/harmony/docs/mobile-alignment.md`，再打开对应 Mobile / 共享源码确认语义。
5. 用 `rg` 从页面入口追到 Store、纯逻辑和测试；先确认已有实现和用户未提交改动。
6. 只在 `apps/harmony` 内完成最小修改，补与风险匹配的测试。
7. 顺序执行 Harmony 单测、`assembleHap`、signed HAP 覆盖安装和真实交互检查。
8. 结束前执行 `git diff --check -- apps/harmony`，审阅完整 diff，并如实说明未验证项。

常用定位命令：

```bash
# 列出 Harmony 源码
rg --files apps/harmony/entry/src/main/ets | sort

# 搜某个页面、状态、channel 或用户文案
rg -n "关键词" apps/harmony/entry/src/main/ets apps/harmony/entry/src/test

# 只看 Harmony 改动
git diff -- apps/harmony
git diff --check -- apps/harmony
```

不要修改、提交或依赖 `.idea/`、`.hvigor/`、`oh_modules/`、`entry/build/`、`entry/.test/` 等生成目录。

## 3. 运行时数据流

```text
EntryAbility
  → Index 初始化 AppServices
  → AuthStore 恢复登录态和 token
  → DlClient 连接 Device Link Relay
  → AppServices 建立设备控制链、订阅 topic、分发 push
  → TaskStore / MessageStore / InteractionStore / GoalStore 等更新
  → TaskListPage / TaskPage 订阅 Store 并刷新 ArkUI
```

桌面端始终是任务、消息和执行状态的权威来源。Harmony 的本地持久化只保存登录凭证、草稿、列表偏好等客户端状态，不能替代远端事实。

```text
apps/harmony/
├── AppScope/                    # 应用级身份、版本、名称与图标资源
├── docs/                        # Harmony 专项产品、架构、行为与验证文档
├── entry/                       # 当前唯一 HAP 模块：源码、资源、测试和产物
├── hvigor/                      # Hvigor 工程配置
├── build-profile.json5         # SDK、产品、构建模式和现有签名配置
├── code-linter.json5           # ArkTS / ArkUI lint 规则
├── hvigorfile.ts               # 工程级 Hvigor 插件入口
├── oh-package.json5            # 工程级 OHPM 依赖
├── oh-package-lock.json5       # OHPM 锁文件
├── local.properties            # 本机 DevEco / SDK 路径，不作为跨机器事实源
└── 项目鸿蒙端开发指南.md        # 本文
```

| 路径 | 作用 | 修改时注意 |
|---|---|---|
| `AppScope/app.json5` | bundle、vendor、版本号和应用图标 | 修改应用身份、版本或区域前先读对应产品规则 |
| `AppScope/resources/` | 应用级名称和图标资源 | 与 `entry` 页面级资源区分开 |
| `docs/` | Harmony 专项设计与行为资料 | 详细状态机留在专项文档，本文只负责导航 |
| `entry/` | 唯一 HAP 模块 | 日常业务开发主要在这里 |
| `hvigor/hvigor-config.json5` | Hvigor 配置 | 通常无需修改 |
| `build-profile.json5` | product、API 24、debug/release 与签名配置 | 含现有本机签名材料信息，禁止复制到文档、日志或提交说明；不得为绕过签名错误擅改 |
| `code-linter.json5` | 静态检查规则 | 不通过弱化规则制造通过 |
| `oh-package.json5` | 工程级测试依赖 | Harmony 工程不按 pnpm / Expo 工程处理 |

修改对外版本时要同时核对 `AppScope/app.json5` 的 `versionName` / `versionCode` 与 `entry/src/main/ets/AppConfig.ets` 的 `appVersion`，避免安装包版本和 Device Link 上报版本漂移。

以下均为本地或构建生成内容，不是源码：

| 路径 | 作用 |
|---|---|
| `.idea/` | DevEco Studio 工程状态 |
| `.hvigor/` | Hvigor 同步缓存和日志 |
| `oh_modules/` | OHPM 安装依赖 |
| `entry/build/` | HAP、source map 和中间构建产物 |
| `entry/.test/` | 本地单测生成代码、缓存与报告；HTML 报告在 `.test/default/outputs/test/reports/index.html` |

## 5. `entry` 模块与源码目录

### 5.1 `entry` 顶层

```text
entry/
├── build-profile.json5         # entry 模块构建选项与 target
├── hvigorfile.ts               # HAP 模块 Hvigor 插件入口
├── obfuscation-rules.txt       # release 混淆规则；当前未启用混淆
├── oh-package.json5            # entry 模块依赖
└── src/
    ├── main/                   # 正式运行代码和资源
    ├── test/                   # 主机侧纯 ArkTS 单元测试
    ├── ohosTest/               # 设备 / 模拟器侧系统能力测试
    └── mock/                   # Harmony 测试 mock 配置
```

`entry/src/main/module.json5` 是 Stage 模块声明，管理：

- 主 Ability：`EntryAbility`；
- 设备类型：phone；
- `INTERNET` 权限；
- 页面路由清单；
- `cindy://session` 深链；
- backup extension。

新增页面时，除创建 `pages/*.ets` 外，还要更新 `entry/src/main/resources/base/profile/main_pages.json`。

### 5.2 正式 ArkTS 源码

```text
entry/src/main/ets/
├── AppConfig.ets               # 区域端点、客户端身份、locale、appVersion
├── entryability/               # 应用 / 窗口 / 前后台生命周期和深链接收
├── entrybackupability/         # 系统备份扩展
├── pages/                      # 页面布局和页面内交互
├── components/                 # 跨页面 ArkUI 组件和 UI token
├── core/                       # Store、协议、解析、投影和业务状态机
└── network/                    # Harmony HTTP / WebSocket 系统 API 适配
```

| 目录 | 作用 | 关键入口 |
|---|---|---|
| `entryability/` | Ability、窗口、系统栏、前后台、Want / 深链生命周期 | `EntryAbility.ets` |
| `entrybackupability/` | backup extension；当前配置不恢复业务数据 | `EntryBackupAbility.ets` |
| `pages/` | 页面布局、导航、builder 与交互接线 | `Index.ets`、`TaskListPage.ets`、`TaskPage.ets` |
| `components/` | 可复用输入区、字体、圆角、动效、点击反馈和 transition | `ConversationComposer.ets`、`UiKit.ets` |
| `core/` | 长生命周期业务状态、协议适配、数据解析和纯逻辑 | `AppServices.ets` |
| `network/` | 对 HarmonyOS HTTP / WebSocket API 的薄封装 | `HarmonyHttp.ets`、`HarmonyWsAdapter.ets`、`WsAdapter.ets` |

### 5.3 页面目录 `pages/`

| 文件 | 当前职责 |
|---|---|
| `Index.ets` | 冷启动入口：初始化 `AppServices`、恢复登录态，进入登录页或任务列表 |
| `LoginPage.ets` | 手机验证码登录 |
| `TaskListPage.ets` | 主页面：设备范围、项目 / 对话 / 自动化 Tab、搜索、排序、折叠、任务操作和宽屏分栏 |
| `TaskListPresentation.ets` | 任务分类、标题、项目名、时间和排序等纯展示逻辑 |
| `TaskSplitLayout.ets` | 平板 / 展开态分栏断点、宽度和拖拽比例纯逻辑 |
| `NewSessionPage.ets` | 新建或编辑任务：Agent、模型、权限、工作目录、附件、首条消息和恢复 |
| `TaskPage.ets` | 会话详情：消息流、工作过程、Tool / Todo、Composer、附件、交互请求、搜索、分页和媒体预览 |
| `SettingsPage.ets` | 设置入口和退出登录 |

当前大量会话 builder 仍集中在 `TaskPage.ets`，任务列表 UI 集中在 `TaskListPage.ets`。不要按早期架构草图假设每种卡片都已有独立组件。

### 5.4 共享组件 `components/`

| 文件 | 作用 |
|---|---|
| `ConversationComposer.ets` | 任务页输入区：文本、图片 / 文件、结构化 atom、模型 chip、发送和停止 |
| `UiKit.ets` | 字体缩放、圆角、点击反馈、动效时长 / 曲线、overlay / reveal transition 等共享 token |

需要统一多个页面的视觉或动效时，优先在 `UiKit.ets` 或语义资源中建立统一口径，不在页面散落数值补丁。

### 5.5 `core/` 业务目录

| 路径 | 作用 | 关键入口 |
|---|---|---|
| `core/AppServices.ets` | 应用级单例组装；连接 Auth、Device Link 和各 Store，管理设备链、全局订阅、push 分发、重连恢复与深链 | 页面获取应用服务的总入口 |
| `core/ComposerCatalog.ets` | 任务页与新建页共享的 provider、模型、权限模式和推理强度目录 | 改模型 / 权限菜单先看这里 |
| `core/auth/` | 验证码、登录、token 刷新、登录态恢复和退出 | `AuthApi.ets`、`AuthStore.ets` |
| `core/device-link/` | envelope、channel、握手、心跳、invoke、订阅、presence 和重连 | `DlProtocol.ets`、`DlClient.ets` |
| `core/tasks/` | 设备 / 任务模型、列表状态、新任务创建、偏好、Agent 切换和 Pi 分支树 | `TaskModels.ets`、`TaskStore.ets` |
| `core/messages/` | 历史、流式合并、发送队列、渲染投影、Markdown、Tool / Todo、搜索、草稿和媒体状态 | `MessageStore.ets`、`MessageRender.ets` |
| `core/attachments/` | 选图、预处理、presign、上传、OSS 引用以及图片 / 文件 Composer 队列 | `ComposerImageQueue.ets`、`ComposerFileQueue.ets` |
| `core/interactions/` | Permission、Ask User、Plan Review 的 pending、草稿、resolve 和展示投影 | `InteractionStore.ets`、`InteractionPresentation.ets` |
| `core/goals/` | Goal mode 状态和 start / clear / pause / resume | `GoalModels.ets`、`GoalStore.ets` |
| `core/navigation/` | `cindy://session/...` 深链解析 | `SessionDeepLink.ets` |
| `core/storage/` | Preferences 持久化包装；保存 token、deviceId 和本地偏好 | `SecureStore.ets` |
| `core/dev/` | HTTP、WebSocket Header 和 storage 的设备探针 | `SystemProbe.ets`；只用于 `ohosTest` 或临时诊断 |

### 5.6 资源目录

```text
entry/src/main/resources/
├── base/
│   ├── element/                # Light 默认颜色、字符串和尺寸
```

| 路径 | 作用 |
|---|---|

| `base/element/string.json` | 模块和 Ability 资源字符串 |

`AppScope/resources` 是应用级名称 / 图标，`entry/src/main/resources` 是模块页面使用的主题和媒体；不要混放。

## 6. 需求到代码定位表

| 要修改的能力 | 先读 | Harmony 主要入口 | 最少验证 |

| 新建任务 | `docs/mobile-alignment.md` | `NewSessionPage.ets` → `ComposerCatalog.ets` → `NewSessionCreationStore.ets` | 创建中、失败恢复、首条消息、附件 |

## 7. 开发步骤：从需求到可交付结果

### 7.1 明确行为和范围

1. 确认问题属于页面呈现、业务 Store、协议适配还是系统能力。
2. 检查 `git status` 和相关文件 diff，区分用户已有改动与本次工作。
3. 用户可见行为先找 Mobile / 共享事实源，写下阈值、状态、错误和降级语义。
4. 如果 Harmony 必须偏离 Mobile，在 `docs/decision-log.md` 记录原因和替代方案。

不要仅凭截图猜协议字段、分页边界、上传状态或交互 decision 结构。

### 7.2 从页面追到数据源

推荐按以下方向阅读：

```text
用户看到的页面 / builder
  → 页面依赖的 Presentation 或 View State
  → Store 的状态、订阅和远程动作
  → AppServices 的 push / reconnect 分发
  → DlClient / DlProtocol 的 channel 与 envelope
```

若只是视觉问题，也要确认节点身份和状态来源；很多“闪黑、一直上传中、点击没反应”实际来自 ArkUI 重建、普通对象原地修改或远程 invoke 错误未解包，不只是颜色问题。

### 7.3 实现时的 ArkUI 约束

- `@State` 中的数组、Map 和对象更新时优先替换引用；只原地修改普通对象可能不触发重绘。
- `ForEach` key 既要稳定识别业务条目，也要在必须重建节点的状态代次变化时反映该代次；禁止使用随机 key。
- Tab / 列表切换要保留页面身份并用位移进入，避免条件分支瞬间销毁重建造成闪烁。
- 纯滑块、Tab 等不需要按压底色的控件关闭不必要的 `stateEffect`；仍要保留可访问性文字。
- 动画优先 transform / opacity；涉及高刷新率时设置合理的 `ExpectedFrameRateRange`，同时尊重“减弱动态效果”。
- Light / Dark 颜色必须走 `base` 与 `dark` 同名 token，不在 ArkTS 写主题判断补丁。
- Store 的远程错误必须进入可见状态或明确 toast；不能吞掉失败后假装成功。
- Device Link `invoke` 返回的是 envelope 时必须按现有 Store 写法解包并校验业务结果。

### 7.4 测试落点

- 新增解析、比较、状态机或展示投影：在 `LocalUnit.test.ets` 增加最小输入、边界输入和失败输入。
- 修复 Store：至少覆盖状态变化、旧响应覆盖、新旧代次或重试语义。
- 修复 ArkUI 接线：单测覆盖底层投影，模拟器实际点击覆盖页面响应。
- 改 Device Link / HTTP / WebSocket：除纯逻辑单测外，补断线、超时和恢复检查。
- 改附件：覆盖 uploading / ready / failed、重试代次、预览和发送后回收。
- 改消息：覆盖历史与实时、Tool 配对、流式更新、分页和滚动锚点。

### 9.1 DevEco CLI、官方文档与 Skills

DevEco CLI 应从 `apps/harmony` 执行工程命令。它会包装 DevEco Studio 自带的 Hvigor、OHPM、HDC、模拟器和 hilog；使用前仍须遵守本文的顺序构建、现有签名和模拟器选择规则。尤其禁止采用通用 Skill 中的 `run --uninstall` 建议处理签名冲突。

当前 Harmony 工程推荐安装以下专项 Skill：

### 9.2 DevEco MCP 语法检查

DevEco MCP 提供 `check` 工具，对 `.ets` 和 C/C++ 文件调用 DevEco 语言服务做静态语法检查。它是本地 `stdio` MCP，不是 HTTP 服务：

```bash
PROJECT_PATH=/path/to/cindy-harmony/apps/harmony \
  devecocli serve mcp
```

为 DevEco CLI 原生支持的 Agent 生成工程级配置：

```bash
devecocli init \
  --mcp \
  --agent codex,claude-code \
  --project /path/to/cindy-harmony/apps/harmony \
  --force
```

生成位置为 `apps/harmony/.codex/config.toml` 和 `apps/harmony/.mcp.json`。配置带本机绝对工程路径，只用于本机 Agent 集成，不得提交；新建或重启对应 Agent 会话后才会加载。检查时传相对 `apps/harmony` 的源码路径，例如：

```text
使用 deveco-mcp check 检查：
entry/src/main/ets/pages/TaskPage.ets
```

Cindy 的 Pi Agent 不内置通用 `stdio` MCP；Cindy 设置中的“外部工具”只接收远程 HTTP / SSE MCP，不能直接填写 `devecocli serve mcp`。因此 Pi 会话使用已安装的 `deveco-cli` / `hmos-arkts-syntax-checker` Skill 调用 CLI 和构建检查；需要 MCP `check` 工具时，新建 Codex 或 Claude Code 会话。不要为接入 MCP 常驻未经管理的本地 HTTP 转接进程。

MCP 首次初始化可能执行 OHPM 同步并建立 ArkTS 索引。不要在测试或构建正在运行时同时触发首次检查；若遇到 Hvigor 锁，等待当前任务结束后顺序重试。MCP 只补充单文件诊断，不替代第 10 节单测和完整 HAP 构建。

## 10. 单元测试与 HAP 构建

测试和构建必须顺序执行，同一个 Harmony 工程不要并行启动多个 Hvigor 任务。

```bash
cd /path/to/cindy-harmony/apps/harmony

# 主机侧 ArkTS 单元测试
NODE_HOME="$HARMONY_NODE_ROOT" JAVA_HOME="$HARMONY_JAVA_ROOT" \
  "$HARMONY_HVIGOR" test \
  --mode module \
  -p product=default \
  -p module=entry@default

# debug HAP
NODE_HOME="$HARMONY_NODE_ROOT" JAVA_HOME="$HARMONY_JAVA_ROOT" \
  "$HARMONY_HVIGOR" assembleHap \
  --mode module \
  -p product=default \
  -p module=entry@default \
  -p buildMode=debug
```

本任务的测试、构建和静态检查只在 `apps/harmony` 内执行，不为 Harmony 改动运行仓库根或其他客户端的测试。

构建成功后的签名产物：

```text
entry/build/default/outputs/default/entry-default-signed.hap
```

设备已有 Cindy 时只能安装 signed HAP。禁止用 `entry-default-unsigned.hap` 覆盖已有应用。

构建排障日志位于 `.hvigor/outputs/build-logs/build.log`。`ohosTest` 依赖设备或模拟器系统能力，不属于上述默认本地门禁；需要时通过 DevEco Studio 运行对应测试 target，并明确记录运行设备。

## 11. 安装、启动和模拟器验证

先在 DevEco Studio Device Manager 启动目标模拟器，再解析目标：

```bash
"$HARMONY_HDC" list targets -v
```

只有目标列表中的模拟器状态为 `Connected` 后才能继续。如果同时存在模拟器和 USB 真机，必须明确选择模拟器；未经用户明确要求，不操作真实设备。把实际模拟器 ID 写入任务专用变量：

```bash
# 常见模拟器 ID 示例；必须以 list targets -v 中 Connected 的模拟器行为准
export HARMONY_TARGET_ID=127.0.0.1:5555
export HARMONY_SIGNED_HAP="$PWD/entry/build/default/outputs/default/entry-default-signed.hap"

if [ ! -f "$HARMONY_SIGNED_HAP" ]; then
  echo "signed HAP 不存在，停止安装"
  exit 1
fi
"$HARMONY_HDC" -t "$HARMONY_TARGET_ID" install -r "$HARMONY_SIGNED_HAP"
"$HARMONY_HDC" -t "$HARMONY_TARGET_ID" shell aa force-stop com.eno.cindy
"$HARMONY_HDC" -t "$HARMONY_TARGET_ID" shell aa start -a EntryAbility -b com.eno.cindy
```

签名与数据安全底线：

- 只允许使用现有配置生成的 `entry-default-signed.hap` 做覆盖安装。
- 禁止为绕过签名问题执行 uninstall、清理应用数据或重置模拟器。
- 如果签名材料不可用、signed HAP 不存在，或 `install -r` 报签名不一致，立即停止并交给用户在 DevEco Studio 中处理。
- 不自行修改 `signingConfigs.default`，不把签名字段打印到日志或粘贴进文档。

## 13. 常见问题定位

| 现象 | 优先检查 |
|---|---|
| `Current process status is busy` | 另一个 Hvigor 任务仍在运行；等待结束后顺序重试，必要时执行 `"$HARMONY_HVIGOR" --stop-daemon` |
| `list targets` 为空 | Device Manager 是否已启动模拟器、HDC 路径是否属于当前 DevEco SDK |
| 安装后还是旧画面 | 确认本次 `assembleHap` 成功、signed HAP 存在、目标 ID 正确且 `install -r` 成功，再 force-stop / start；Hvigor 可能命中缓存，不要只靠时间戳判断 |
| `install sign info inconsistent` | HAP 与已安装应用签名不一致；停止并交给用户处理，禁止清数据 |
| 点击后视觉不变化 | `@State` 是否替换了对象 / Map / 数组引用，Store 是否 notify，按钮是否被 overlay 或 busy 状态挡住 |
| 列表一直显示旧上传状态 | `ForEach` key 是否包含必要的状态 / revision，队列是否原地修改后触发页面响应式刷新 |
| Tab 或列表切换闪黑 | 是否因条件分支销毁重建页面、是否使用按压 stateEffect、列表内容是否有稳定节点身份和方向动画 |
| 远程选择 / 操作点击无结果 | Interaction / Store 是否进入 resolving、invoke envelope 是否解包、业务错误是否进入 UI |
| 历史重复或断层 | `MessageStore` 的窗口覆盖、稳定 key、push 合并、gap healing 与重连补拉 |
| 页面有数据但与 Mobile 不一致 | 回到 Mobile / 共享事实源核对阈值、配对、状态机和降级路径，不在 ArkUI 层继续打补丁 |

## 14. 最小交付门槛

准备提交或推送前，先读根 `docs/dev-rules/development-workflow.md`。只暂存本次 Harmony 文件；提交使用 `git commit -s` 保留 DCO，push 仍需用户明确授权。

- 只修改任务需要的 Harmony 模块，未覆盖或回退用户已有改动。
- 用户可见行为已与对应 Mobile / 共享实现核对；需要偏离时有决策记录。
- 可测试的解析、投影和状态机已有单测，Harmony 单元测试通过。
- `assembleHap` 通过并生成 `entry-default-signed.hap`。
- signed HAP 已覆盖安装到明确的模拟器目标，核心交互实际操作过。
- UI 改动使用语义 token，并检查 Light / Dark；未能目检的模式如实说明。
- `git diff --check -- apps/harmony` 通过，完整 diff 已人工审阅。
- 没有提交生成目录、签名材料、凭证、设备数据或无关文件。
- 交付说明列出已验证、未验证、剩余风险和设备范围。
